# ADR 0002 — GCP como plataforma de despliegue (staging y piloto)

**Estado:** aceptado (decisión del CTO, 2026-08-14).
**Fecha:** 2026-08-14
**Sustituye a:** [ADR 0001 — Railway vs Fly.io](0001-railway-vs-flyio.md), que queda **anulado**.
**Contexto:** QUI-213 · [`docs/plan-finalizacion-piloto.md`](../plan-finalizacion-piloto.md)
§"Arquitectura de despliegue en GCP" · doc técnico §10.

## Problema

El proyecto necesita, por primera vez, **infraestructura desplegada de verdad**: hasta hoy no
existe ningún entorno más allá del `docker-compose.yml` local, y sin él no se puede correr el
load test (QUI-250), ni el preflight del piloto, ni verificar RLS contra un Postgres gestionado.

Lo que hay que alojar:

- `apps/api` — NestJS/Fastify, HTTP.
- El **worker de ingesta GPS** — consumidor BullMQ, proceso separado, sin modelo de request.
- El **job de retención GPS** — batch periódico.
- Postgres 16 **con PostGIS** (extensión obligatoria: `rutas.geometria`, `paradas.coord`,
  `puntos_control.coord` son `GEOGRAPHY`, y `ST_DWithin` corre en la ruta caliente).
- Redis (BullMQ).
- `apps/web` — Next.js 15 App Router.
- Secretos: `RUNTIME_DATABASE_URL`, `JWT_SECRET`, credenciales de R2.

## Por qué se anula el ADR 0001

El ADR 0001 comparaba Railway y Fly.io, nunca se ejecutó, y quedó obsoleto por un hecho
externo: **la cuenta de GCP de la organización se reactivó**. Con crédito y facturación ya
resueltos en GCP, evaluar dos proveedores nuevos es trabajo sin retorno. La decisión del CTO
(2026-08-14) es GCP.

## Decisión

| Componente | Servicio | Por qué |
|---|---|---|
| `apps/api` | **Cloud Run** service, `min-instances=1` | HTTP, escala por request; `min-instances=1` evita el arranque en frío en un piloto con conductores en la calle |
| Worker de ingesta | **Cloud Run Worker Pools** | Llegó a GA en abril de 2026 y es exactamente el caso: instancias persistentes que consumen una cola, sin modelo de request. Con un *service* normal el worker moriría por falta de tráfico |
| Retención GPS | **Cloud Run Job + Cloud Scheduler** | Es batch periódico, no consumidor continuo. Un worker pool para esto sería una instancia despierta 24/7 sin trabajo |
| Postgres | **Cloud SQL** PG16 + PostGIS | PostGIS soportado (`CREATE EXTENSION postgis`) |
| Redis | **Memorystore** Basic | Sin réplica: para el piloto, perder la cola es reintento del cliente, no pérdida de evidencia (el outbox del teléfono es la fuente durable) |
| Secretos | **Secret Manager** | Service account dedicada de mínimo privilegio |
| `apps/web` | **Firebase App Hosting** | Soporte de primera de Next.js 15 App Router dentro de GCP; evita un proveedor más |
| Archivado GPS | **Cloudflare R2** (fuera de GCP, a propósito) | Ver abajo |
| IaC | **Terraform**, state en GCS | Ver abajo |

```
Internet ──▶ Cloud Run: apps/api (min-instances=1)
                  │ Direct VPC egress
     ┌────────────┼──────────────┐
     ▼            ▼              ▼
 Cloud SQL   Memorystore    Secret Manager
 PG16+PostGIS  Redis Basic   (RUNTIME_DATABASE_URL,
                  │           JWT_SECRET, R2)
                  │ BullMQ
        Cloud Run WORKER POOL ── ingesta GPS (always-on, 1 instancia)
        Cloud Run JOB + Scheduler ── retención GPS (batch) ──▶ Cloudflare R2

 apps/web (Next.js 15) ──▶ Firebase App Hosting
```

### Decisiones que conviene no revertir sin leer esto

- **Worker pools son de escalado manual**, no autoscalan por profundidad de cola. Para el
  piloto (40 vehículos, ~1,3% de la carga de diseño) 1 instancia fija sobra; en régimen hay que
  dimensionarlas a mano o volver a evaluar.
- **Cloud SQL, no AlloyDB.** AlloyDB recién empata en costo pasando ~1,75 TiB, y estamos lejos.
- **RLS funciona en Cloud SQL.** El usuario `postgres` de Cloud SQL **no es superusuario real**
  (es `cloudsqlsuperuser`), así que `CREATE ROLE quivo_app` sin BYPASSRLS y `FORCE ROW LEVEL
  SECURITY` se comportan igual que en Postgres vanilla — que es el supuesto sobre el que se
  construyó todo el aislamiento multi-tenant (QUI-218). **Verificación obligatoria antes del
  primer deploy productivo:** correr `packages/db/src/rls.integration.test.ts` contra la
  instancia real de Cloud SQL, no solo contra el Docker local.
- **Archivado en Cloudflare R2, no GCS.** Es la única pieza deliberadamente fuera de GCP: el
  egreso de R2 es **$0 permanente** contra ~$0,12/GB de GCS, y evita un footgun conocido (las
  versiones recientes del AWS SDK activan checksums que rompen contra GCS salvo que se seteen
  dos variables de entorno). Cero cambio de código — el archivado ya está implementado contra
  la API S3.
- **Terraform, no scripts de `gcloud`.** La razón es concreta: da un `plan`/diff revisable antes
  de tocar infra, que es la barandilla que importa con una pasante junior en el equipo, y usa el
  mismo flujo de PR que ya usa el código.
- **`secretAccessor` se otorga antes del primer deploy.** Cloud Run valida el acceso a los
  secretos en tiempo de deploy y falla si el permiso no está.

## Trampa principal a resolver antes de producción

Cloud SQL tiene límite de conexiones y el proyecto **no tiene PgBouncer ni `connection_limit`
explícito**; además hay dos pools independientes (Prisma y el de `HealthService`). Con la API
escalando horizontalmente más el worker, un burst de reconexión de flota puede agotar las
conexiones de un tier chico. Mitigación mínima para el piloto: `connection_limit` explícito en
la URL y `max-instances` capado (N16 del plan). PgBouncer y réplicas de lectura quedan para M7.

## Costo

~US$160–230/mes para el piloto; ~US$1.200–2.800/mes en régimen de 3000 vehículos.

El objetivo declarado en el documento técnico §10/§13 era US$50–150/mes: **no es alcanzable**
con servicios gestionados en región sudamericana, y esta decisión lo acepta explícitamente.
Palancas si el número molesta: desplegar en `us-central1` (~35% más barato, a costa de latencia
sin medir) o Redis en una VM en vez de Memorystore (~US$25/mes menos, a costa de ops manual).

## Abierto

- **Región.** Lean por `southamerica-east1` (São Paulo): catálogo más completo y ruta terrestre
  mejorando con el Corredor Bioceánico. **No hay dato duro de latencia desde Bolivia** — correr
  `gcping.com` desde una conexión boliviana antes de comprometerse. Es reversible barato hoy
  (nada aprovisionado) y caro después (migración de datos).
- **OSRM** (pegado de rutas a las calles en el editor) no se despliega: requiere una VM dedicada
  con el extracto vial de Bolivia. Para el piloto las rutas se dibujan una vez con OSRM local y
  se siembran; el editor queda degradado en staging, documentado.

## Consecuencias

- QUI-213 se rescopea de 3 a 5 puntos (Cloud Run API + Worker Pool, Cloud SQL PostGIS,
  Memorystore, Secret Manager, Terraform) y se ejecuta en F2 (C17–C18) del plan de finalización.
- Aparece trabajo que no estaba tiqueteado: `Dockerfile` (una imagen, dos `CMD`),
  `enableShutdownHooks()` en `apps/api/src/main.ts` — sin él los `OnModuleDestroy` no corren
  ante el SIGTERM de Cloud Run — y separar liveness de readiness (N6).
- `JWT_SECRET` y `RUNTIME_DATABASE_URL` son dependencia dura del primer deploy: arrancar sin
  `JWT_SECRET` debe fallar ruidosamente (N11), arrancar sin `RUNTIME_DATABASE_URL` ya falla.
- El deploy de `apps/web` deja de apuntar a Vercel en todos los documentos de stack.
