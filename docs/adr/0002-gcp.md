# ADR 0002 — GCP como plataforma de despliegue (staging y piloto)

**Estado:** aceptado (decisión del CTO, 2026-08-14).
**Fecha:** 2026-08-14
**Sustituye a:** [ADR 0001 — Railway vs Fly.io](../archivo/0001-railway-vs-flyio.md), que queda **anulado**.
**Contexto:** QUI-213 · [`docs/archivo/plan-finalizacion-piloto.md`](../archivo/plan-finalizacion-piloto.md)
§"Arquitectura de despliegue en GCP" · doc técnico §10.

## Problema

El proyecto necesita, por primera vez, **infraestructura desplegada de verdad**: hasta hoy no
existe ningún entorno más allá del `docker-compose.yml` local, y sin él no se puede correr el
load test (QUI-250), ni el preflight del piloto, ni verificar RLS contra un Postgres gestionado.

Lo que hay que alojar:

- `apps/api` — NestJS/Fastify, HTTP.
- El **worker de ingesta GPS** — consumidor BullMQ, proceso separado, sin modelo de request.
- El **job de retención GPS** — batch periódico.
- Postgres 16 **con PostGIS** (extensión obligatoria: `rutas.geometria`, `paradas.coord`,
  `puntos_control.coord` son `GEOGRAPHY`, y `ST_DWithin` corre en la ruta caliente).
- Redis (BullMQ).
- `apps/web` — Next.js 15 App Router.
- Secretos: `RUNTIME_DATABASE_URL`, `JWT_SECRET`, credenciales de R2.

## Por qué se anula el ADR 0001

El ADR 0001 comparaba Railway y Fly.io, nunca se ejecutó, y quedó obsoleto por un hecho
externo: **la cuenta de GCP de la organización se reactivó**. Con crédito y facturación ya
resueltos en GCP, evaluar dos proveedores nuevos es trabajo sin retorno. La decisión del CTO
(2026-08-14) es GCP.

## Decisión

**Región: `southamerica-west1` (Santiago de Chile).** Ver §Región abajo — se midió, no se asumió.

| Componente | Servicio | Por qué |
|---|---|---|
| `apps/api` | **Cloud Run** service, `min-instances=1` | HTTP, escala por request; `min-instances=1` evita el arranque en frío en un piloto con conductores en la calle |
| Worker de ingesta | **Cloud Run Worker Pools** | Llegó a GA en abril de 2026 y es exactamente el caso: instancias persistentes que consumen una cola, sin modelo de request. Con un *service* normal el worker moriría por falta de tráfico |
| Retención GPS | **Cloud Run Job** + **Cloud Scheduler en `southamerica-east1`** | Es batch periódico, no consumidor continuo. Un worker pool para esto sería una instancia despierta 24/7 sin trabajo. El Scheduler va en São Paulo por fuerza mayor — ver §Región |
| Postgres | **Cloud SQL** PG16 + PostGIS | PostGIS soportado (`CREATE EXTENSION postgis`) |
| Redis | **Memorystore** Basic | Sin réplica: para el piloto, perder la cola es reintento del cliente, no pérdida de evidencia (el outbox del teléfono es la fuente durable) |
| Secretos | **Secret Manager** | Service account dedicada de mínimo privilegio |
| `apps/web` | **Cloud Run** service | **No Firebase App Hosting** — ver abajo |
| Archivado GPS | **Cloudflare R2** (fuera de GCP, a propósito) | Ver abajo |
| IaC | **Terraform**, state en GCS | Ver abajo |

```
                        southamerica-west1 (Santiago)
Internet ──▶ Cloud Run: apps/api (min-instances=1)
     │            │ Direct VPC egress
     │ ┌──────────┼──────────────┐
     │ ▼          ▼              ▼
     │ Cloud SQL  Memorystore  Secret Manager
     │ PG16+PostGIS Redis Basic (RUNTIME_DATABASE_URL,
     │              │            JWT_SECRET, R2)
     │              │ BullMQ
     │     Cloud Run WORKER POOL ── ingesta GPS (always-on, 1 instancia)
     │     Cloud Run JOB ── retención GPS (batch) ──▶ Cloudflare R2
     │            ▲
     │            └── Cloud Scheduler (southamerica-east1) · 1 disparo/día
     │
     └──▶ Cloud Run: apps/web (Next.js 15)
```

### `apps/web` va en Cloud Run, no en Firebase App Hosting

Firebase App Hosting **no tiene ninguna región sudamericana** (soporta `us-central1`,
`us-east4`, `us-east5`, `asia-east1`, `asia-southeast1`, `europe-west4`), así que elegirlo
obligaba a servir el panel desde EE.UU. — 199 ms desde La Paz, medidos — con un proveedor y un
camino de deploy extra en el Terraform.

Y no compra nada a cambio: se verificó que **todo `page`/`layout` de `apps/web` salvo
`app/layout.tsx` es `'use client'`**, y el fetching es TanStack Query contra
`NEXT_PUBLIC_API_URL` desde el navegador (`apps/web/src/lib/api/client.ts`). El panel es un SPA
con cáscara Next.js: **el host web no está en el camino de datos**, el browser pega directo
contra la API. Sin SSR con datos, sin Server Actions y sin ISR, la única ventaja de App Hosting
no aplica.

Servirlo como un Cloud Run más deja todo en una plataforma, un proveedor de Terraform y un
camino de deploy, en la misma región que la API. **Si en el futuro `apps/web` incorpora SSR con
datos reales, esta decisión hay que revisarla** — ahí sí importaría dónde corre el render.

### Decisiones que conviene no revertir sin leer esto

- **Worker pools son de escalado manual**, no autoscalan por profundidad de cola. Para el
  piloto (40 vehículos, ~1,3% de la carga de diseño) 1 instancia fija sobra; en régimen hay que
  dimensionarlas a mano o volver a evaluar.
- **Cloud SQL, no AlloyDB.** AlloyDB recién empata en costo pasando ~1,75 TiB, y estamos lejos.
- **RLS funciona en Cloud SQL.** El usuario `postgres` de Cloud SQL **no es superusuario real**
  (es `cloudsqlsuperuser`), así que `CREATE ROLE quivo_app` sin BYPASSRLS y `FORCE ROW LEVEL
  SECURITY` se comportan igual que en Postgres vanilla — que es el supuesto sobre el que se
  construyó todo el aislamiento multi-tenant (QUI-218). **Verificación obligatoria antes del
  primer deploy productivo:** correr `packages/db/src/rls.integration.test.ts` contra la
  instancia real de Cloud SQL, no solo contra el Docker local.
- **Archivado en Cloudflare R2, no GCS.** Es la única pieza deliberadamente fuera de GCP: el
  egreso de R2 es **$0 permanente** contra ~$0,12/GB de GCS, y evita un footgun conocido (las
  versiones recientes del AWS SDK activan checksums que rompen contra GCS salvo que se seteen
  dos variables de entorno). Cero cambio de código — el archivado ya está implementado contra
  la API S3.
- **Terraform, no scripts de `gcloud`.** La razón es concreta: da un `plan`/diff revisable antes
  de tocar infra, que es la barandilla que importa con una pasante junior en el equipo, y usa el
  mismo flujo de PR que ya usa el código.
- **`secretAccessor` se otorga antes del primer deploy.** Cloud Run valida el acceso a los
  secretos en tiempo de deploy y falla si el permiso no está.

## Trampa principal a resolver antes de producción

Cloud SQL tiene límite de conexiones y el proyecto **no tiene PgBouncer ni `connection_limit`
explícito**; además hay dos pools independientes (Prisma y el de `HealthService`). Con la API
escalando horizontalmente más el worker, un burst de reconexión de flota puede agotar las
conexiones de un tier chico. Mitigación mínima para el piloto: `connection_limit` explícito en
la URL y `max-instances` capado (N16 del plan). PgBouncer y réplicas de lectura quedan para M7.

## Región: `southamerica-west1` (Santiago)

El plan de finalización venía con un *lean* por São Paulo apoyado en dos supuestos —"catálogo
más completo" y una intuición geográfica— y advertía que **no había dato duro de latencia**. Se
midió. Los dos supuestos resultaron falsos.

**Latencia real, medida el 2026-08-14 desde una conexión boliviana** (La Paz, AXS Bolivia,
`AS26210`). Método: 12 requests HTTPS sobre una **única conexión TLS reusada** por región,
descartando el handshake, contra los endpoints de `gcping.com` (Cloud Run, un servicio por
región); n=11 warm, dos corridas consistentes.

| Región | RTT mediana | p90 |
|---|---|---|
| **`southamerica-west1`** (Santiago) | **52 ms** | 53 ms |
| `southamerica-east1` (São Paulo) | 110 ms | 115 ms |
| `us-east4` (N. Virginia) | 199 ms | 203 ms |
| `us-central1` (Iowa) | 230 ms | 250 ms |

> **Trampa de medición, documentada para que nadie repita el error:** medir con `time_connect`
> de `curl`, o con conexiones nuevas, da **~40 ms para todas las regiones por igual** — eso es
> el borde Anycast de Google, no el datacenter. La diferencia aparece recién al reusar la
> conexión y medir la respuesta de la aplicación.

**Costo (precio de lista, verificado el 2026-08-14):** Cloud Run y Worker Pools usan un modelo
de **2 tiers**, no precio por región — Santiago y São Paulo son ambas Tier 2 y cuestan
**exactamente lo mismo** en cómputo y egreso. Cloud SQL y Memorystore sí son por región, y ahí
Santiago es más barato: **−6,7%** en Cloud SQL y **−19,5%** en Redis. Total del perfil piloto:
**−6,5% a favor de Santiago**.

Santiago gana en las dos dimensiones a la vez: **la mitad de latencia y más barato.** No hay
tradeoff que deliberar.

### Lo que Santiago no tiene, y por qué no bloquea

- **Cloud Scheduler no existe en `southamerica-west1`** (verificado en la doc oficial de
  ubicaciones; São Paulo es la única región sudamericana). En esta arquitectura el Scheduler
  hace **una sola cosa: disparar el Job de retención GPS, una vez por día**. Un Scheduler en
  `southamerica-east1` apuntando al Job en Santiago funciona —el endpoint de la Cloud Run Admin
  API es global— y cuesta ~30 ms extra en una llamada diaria. Es la única pieza multi-región del
  despliegue y hay que dejarla explícita en el Terraform para que no parezca un error.
- **Firebase App Hosting no tiene ninguna región sudamericana.** No es un gap de Santiago sino
  del servicio, y se resolvió sacándolo de la arquitectura — ver §`apps/web` arriba.

### Verificado en vivo, no inferido de la documentación

**Cloud Run Worker Pools sí funciona en Santiago.** Es la pieza que sostiene el worker de
ingesta y era el único gap capaz de descartar la región, pero no tiene tabla de regiones
publicada: la doc no documenta restricción y tampoco lo confirma en positivo. Se comprobó contra
la API real con `POST .../locations/southamerica-west1/workerPools?validateOnly=true`, que
**valida sin crear nada**: aceptado en Santiago y en São Paulo, con `Listed 0 items` confirmado
después en ambas. Control de la prueba: la misma llamada contra una región inexistente falla.

No dar por buena la disponibilidad de un servicio nuevo por ausencia de una nota en la doc —
`validateOnly=true` es la forma barata de convertir una inferencia en un hecho.

### Reversibilidad

Hoy cambiar de región es gratis: no hay nada aprovisionado. Después de cargar datos de campo es
una migración con downtime. Esta decisión se toma ahora **por eso**, no a pesar de eso.

## Costo

**Perfil del piloto, precio de lista verificado el 2026-08-14 en `southamerica-west1`:**

| Componente | US$/mes |
|---|---|
| Cloud SQL (2 vCPU / 8 GB / 50 GB SSD, zonal) | 153,52 |
| Memorystore Redis Basic 1 GB | 51,10 |
| Cloud Run Worker Pool (1 vCPU / 512 MiB, always-on) | 37,41 |
| Cloud Run `apps/api` (1 vCPU / 512 MiB, `min-instances=1`) | 10–93 según ocupación (ver abajo) |
| Egreso 20 GB | 3,80 |

**El rango de la API es la diferencia entre facturarse activa o idle.** Los US$92,86 salen de
asumir CPU always-allocated las 24 h; con `min-instances=1` y ~5 admins sobre un piloto de 40
vehículos, la instancia está ociosa casi todo el tiempo y se factura a tarifa idle (~US$10).
Verificarlo con la facturación real del primer mes en vez de asumirlo.

**Esto corrige el ~US$160–230/mes que circulaba en el plan de finalización:** el número realista
es **~US$255–290/mes** para el piloto. La diferencia no es la región (Santiago es más barato que
lo asumido) sino el sizing: **Cloud SQL 2 vCPU/8 GB está sobredimensionado para 40 vehículos** y
es, de lejos, la línea más cara. Bajarlo a 1 vCPU/4 GB acerca el total a la estimación vieja —
decidir el tier con el resultado del k6 (QUI-250), no antes.

El objetivo del documento técnico §10/§13 (US$50–150/mes) **no es alcanzable** con servicios
gestionados en región sudamericana, y esta decisión lo acepta explícitamente. Palancas si el
número molesta: Cloud SQL más chico (la de mayor efecto), Redis en una VM en vez de Memorystore
(~US$25/mes menos, a costa de ops manual) o `us-central1` (~30% más barato **pero 230 ms**, que
es justo lo que esta decisión evita).

Régimen de 3000 vehículos: ~US$1.200–2.800/mes, sin re-verificar en este ADR.

## Abierto

- **OSRM** (pegado de rutas a las calles en el editor) no se despliega: requiere una VM dedicada
  con el extracto vial de Bolivia. Para el piloto las rutas se dibujan una vez con OSRM local y
  se siembran; el editor queda degradado en staging, documentado.
- **Tier definitivo de Cloud SQL**, con el resultado del k6 (QUI-250). Ver §Costo.

## Consecuencias

- QUI-213 se rescopea de 3 a 5 puntos (Cloud Run API + Worker Pool, Cloud SQL PostGIS,
  Memorystore, Secret Manager, Terraform) y se ejecuta en F2 (C17–C18) del plan de finalización.
- Aparece trabajo que no estaba tiqueteado: `Dockerfile` (una imagen, dos `CMD`),
  `enableShutdownHooks()` en `apps/api/src/main.ts` — sin él los `OnModuleDestroy` no corren
  ante el SIGTERM de Cloud Run — y separar liveness de readiness (N6).
- `JWT_SECRET` y `RUNTIME_DATABASE_URL` son dependencia dura del primer deploy: arrancar sin
  `JWT_SECRET` debe fallar ruidosamente (N11), arrancar sin `RUNTIME_DATABASE_URL` ya falla.
- El deploy de `apps/web` deja de apuntar a Vercel en todos los documentos de stack, y **suma un
  `Dockerfile` propio** (Next.js 15 en modo `standalone`) que N6 no tenía previsto: N6 hablaba de
  una imagen con dos `CMD` para API y worker. Ahora son dos imágenes.
- El Terraform queda **multi-región a propósito**: todo en `southamerica-west1` menos el Cloud
  Scheduler, en `southamerica-east1`. Documentarlo en el módulo para que no se lea como un error.
- El presupuesto del piloto pasa de ~US$160–230/mes a **~US$255–290/mes** — ver §Costo. Hay que
  corregirlo donde se cite.
